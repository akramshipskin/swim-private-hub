# Design: Swim Private Hub — 3-sided marketplace pivot

## Problem Statement

Pivot les-renang-cianjur (existing single-pool booking tool, live in production for
one paying pool-owner client) into a separate product, "Swim Private Hub" — a
3-sided marketplace connecting pool venues, independent swim coaches (who float
across multiple pools instead of being tied to one), and members/parents who book
any coach + pool + time. Revenue via commission on each booking, partner-network
model similar to Gojek/Gofood.

## Demand Evidence

Zero direct evidence for the marketplace model specifically. During the forcing
questions, the founder initially claimed a pool owner had asked for this directly,
but when pushed for a name or quote, admitted no such person or quote exists — he
was about to invent one before being stopped. Confirmed: nobody has asked for
independent floating coaches, cross-pool booking, or a commission model.

## Status Quo

This part IS validated: the founder has talked in depth with 3+ pool owners beyond
his existing client, and all of them confirmed they run booking/scheduling manually
via Excel/WhatsApp — the exact operational pain his existing v1 app already solves
for one pool. The underlying pain (manual booking chaos) is real and widespread.
The marketplace-specific pain (wanting to share/hire coaches across pools) is not
evidenced anywhere.

## Target User & Narrowest Wedge

When pushed to name the person who needs this most, the founder named his existing
v1 client — describing consequences ("losing members, everything manual, not
scalable, needs one automated dashboard") that are identical to what v1 already
solves. No marketplace-specific persona was named. This is a real gap: the
"target user" for the *marketplace* specifically has not been identified as a
distinct person from the v1 target user.

## Constraints

- Codebase must be 100% separate from les-renang-cianjur (explicit founder
  requirement — zero shared code, so the existing production app for the current
  paying client is never at risk). Already executed: fresh private GitHub repo
  `swim-private-hub`, cloned with full git history, remote repointed, no shared
  origin. `.env` (real DB/Midtrans credentials) never carried over — needs its
  own Supabase project and credentials from scratch, never reuse the
  les-renang-cianjur production database.
- Legal/business blind spots remain fully unresolved (carried over from a prior
  informal brainstorm, 2026-08-26): liability model (pool facility risk vs coach
  teaching risk — most bookings are for children, so parental consent needs to be
  an explicit form, not a T&C checkbox), coach certification/verification process,
  pricing/commission structure (if coaches set their own price per pool, price
  transparency to members gets complex), the platform's legal posture (pure
  connector like Gojek = lower liability exposure vs. direct service provider =
  higher exposure), and the risk that pools with existing in-house coaches see
  "freeing" their coach as poaching and refuse to partner.
- Technical: current schema (inherited from les-renang-cianjur) has zero
  multi-tenancy concept — no Pool/Tenant model, no poolId anywhere. Booking
  becomes a 2-calendar matching problem (coach AND pool availability both free) —
  today's system only checks one calendar. No rating/trust system exists.

## Data Model Sketch (provisional)

- **Pool**: id, name, address, contact, ownerUserId, midtransMerchantId (nullable
  — see Onboarding note below: not every pool has one on day one).
- **Coach**: id, name, contact — independent entity, NOT owned by a single Pool.
- **PoolAffiliation**: many-to-many join (coachId, poolId) — a coach can be
  affiliated with multiple pools simultaneously; a pool can have multiple
  affiliated coaches.
- **Member**: unchanged concept from v1 (parent/guardian account, has Dependents).
- **Availability**: now needs BOTH coachId and poolId (a coach's slot is only
  bookable at a specific pool at a specific time) — this is the root of the
  "2-calendar matching" problem below. **Concurrency (LOCKED, two separate
  mechanisms, both required — resolved during `/plan-eng-review` 2026-09-12):**
  1. **Creation-time constraint:** `unique(coachId, timeslot)` on Availability
     — no poolId in the constraint. A coach can never hold two open slots for
     the same time at two different pools; a person can't be in two places.
     The doc's original draft used `unique(coachId, poolId, timeslot)`, which
     does not prevent this — caught in review.
  2. **Booking-time row lock:** `SELECT ... FOR UPDATE` on the Availability
     row at Booking creation (check `status = AVAILABLE`, then create Booking
     and flip to `BOOKED` atomically) — same pattern as the existing
     `cancel-booking.ts` row-lock, ported unchanged. This prevents two
     MEMBERS racing to book the same already-open slot — a different failure
     mode than #1, not solved by the uniqueness constraint. Both are
     non-negotiable for Phase 1.
- **Booking**: references Availability (which already pins coach+pool+time),
  Member, Dependent, Payment. **Discovery (LOCKED):** pool-first browse —
  member selects a Pool (same flow as today's single-pool app, minimal new
  UI), then sees that pool's available coach+slot combinations. Scopes the
  Availability query by `poolId`, reuses the existing list UI almost as-is.
  Rejected cross-pool coach search for Phase 1 (real UI/query work for a use
  case — a member with no existing pool relationship — that doesn't exist in
  the network-first GTM plan). **Cross-model caveat, addressed:** pool-first
  alone means a member can't follow a known coach to a different pool. Phase 1
  adds one cheap mitigation: a static per-coach page listing their current
  pool affiliations + a WhatsApp contact link — no search engine, just enough
  for "find my coach elsewhere" to work by word of mouth.
- **Payment (Phase 1 scope, explicit):** a Payment record IS created per
  Booking in Phase 1 — status `manual_pending` — but no automated transfer/split
  happens through Midtrans. If the member's checkout goes through Midtrans in
  Phase 1 (simpler than cash/manual-transfer collection), **it routes to the
  affiliated pool's own Midtrans account, never a platform-owned account** —
  the platform itself never touches or holds member funds, even momentarily,
  during Phase 1. The commission split (pool → coach → platform's cut) happens
  entirely off-platform after that, tracked only by the `manual_pending` status
  field. **This shape assumes a connector legal posture** (platform doesn't
  hold funds) — it is provisional, not a resolved decision: if service-provider
  posture is chosen instead (see Open Questions), Payment needs additional
  fields to actually hold/disburse funds through a platform-owned account,
  which is a bigger schema change than just adding a commission-split column.
  The commission-split payment *shape* Payment eventually needs also depends on
  the pricing/commission question (Open Questions) — both are Phase 2 schema
  work, not Phase 1, but the Phase 1 sketch above is not neutral to how they
  get answered.
- **Booking Lifecycle (deferred detail, named here so it isn't silently
  missing):** cancellation, no-show, and dispute handling (pool vs. coach vs.
  member) are not designed yet. Given the existing single-pool app already has
  a jatah-pembatalan (cancellation allowance) pattern, `/plan-eng-review` should
  start from that pattern rather than from zero — but the 3-way dispute case
  (who's at fault, pool/coach/member) is genuinely new and unresolved.
- **Admin tiers (Phase 1 scoped down):** at Phase 1 pool counts (~4: the v1
  client + 3 interviewed), there's no evidence yet that pool owners NEED their
  own login (vs. the founder coordinating manually, same as today). Phase 1
  ships with the founder as sole platform superadmin; per-pool admin accounts
  (with mandatory poolId-filtered queries) are deferred to Phase 2 — trigger
  is demand-based (a pool operator explicitly asks for their own login), not
  headcount-based (having 4 pools in Phase 1 does not by itself trigger this).
  **Data-isolation gap, closed during `/plan-eng-review`:** today's schema has
  `Role` = ADMIN/COACH/MEMBER with zero pool-scoping — ADMIN means unrestricted
  access to everything. The onboarding flow below must NOT carry a migrated
  pool owner's ADMIN role forward as-is, or that pool owner becomes a de facto
  superadmin able to see every OTHER pool's bookings/members/payments too.
  Only the founder's own account stays ADMIN in Phase 1; migrated owners get a
  non-privileged role. **Accepted tradeoff:** this means the v1 client (and
  the 3 new pools) lose self-service admin entirely in Phase 1 — a real
  regression from what v1 already gives the existing client today, accepted
  as temporary and bounded (~4 pools, founder already has a direct
  relationship with each) until per-pool admin ships in Phase 2.
- **Commission collection (LOCKED, added during `/plan-eng-review`):**
  connector posture + off-platform settlement means `manual_pending` is a data
  label, not a collection mechanism — nothing forces or reminds a pool to
  actually pay the platform's cut. Phase 1 adds one small report/query
  (`GROUP BY poolId` over `manual_pending` Payments × commission %) so the
  founder collects from a real number instead of memory or trust. Not a
  payments feature — a read-only summary, run manually (page or CLI script).

## Onboarding the Existing Network

The founder's GTM plan (Premise 4) is to start with his v1 client + the 3
interviewed pools, not cold strangers. **LOCKED during `/plan-eng-review`:**
Pool + PoolAffiliation records for all 4 known pools are created via a one-off
admin seed script, not a built CRUD UI (Step 0 scope trim — a full admin
management page for something used 4 times total was cut as premature scope).
The migrated User's role is downgraded away from ADMIN as part of this script
(see Admin tiers note above) — the pool owner keeps their login but loses
admin privileges outside their own pool's data, since Phase 1 has no
poolId-scoped query layer to safely let them keep ADMIN. A 5th pool joining
later needs the founder (or a developer) to run the script again — self-serve
onboarding is Phase 2 scope, not Phase 1.

**Midtrans merchant account gap:** the v1 client already has a working Midtrans
merchant account (inherited from les-renang-cianjur). The 3 newly-interviewed
pools almost certainly don't — they currently run Excel/WhatsApp (Status Quo),
not any payment gateway. Each needs to complete its own Midtrans merchant
signup/KYC before Phase 1 checkout can route to `midtransMerchantId` for that
pool. This is real onboarding lead-time (days to weeks, Midtrans-dependent, not
controlled by this project) that Phase 1 planning must account for — a pool
without a registered merchant account simply can't take Midtrans checkout yet
and would need cash/manual-transfer collection as a stopgap.

## Approaches Considered

### Approach A: Concierge Listing Page (Minimal Viable) — NOT chosen
One bare listing/request page in the swim-private-hub repo (coach + pool + slot +
price, WhatsApp "Request" button). No accounts, no matching, no commission engine.
Founder manually dispatches and negotiates commission terms with the existing pool
network first. Effort: S. Risk: Low. Rejected by founder in favor of Approach B —
he wants to build the real architecture, not validate manually first.

### Approach B: Full Marketplace Architecture — CHOSEN, phased
Build the real multi-tenant data model from the start: Pool entity, Coach as an
independent entity with a many-to-many PoolAffiliation, Member, 2-calendar booking
matching (coach AND pool availability). Effort: XL is the honest label even with
AI-assisted build speed — the schema/migration mechanics compress well (day(s) of
focused Claude Code sessions, per this project's established pattern), but the
2-calendar matching correctness (concurrency, double-booking prevention) and the
legal/pricing unknowns do NOT compress, since those need human decisions and
careful correctness work, not just fast typing. Treat "XL" as a real XL, not a
disguised S. Risk: High, primarily from the unresolved pricing/legal questions
below plus the concurrency correctness requirement, not from schema mechanics.

**Phase 1 scope (what actually gets built first):** multi-tenant schema
(Pool/Coach/PoolAffiliation/Availability) with the concurrency constraint above,
2-calendar booking matching, manual (off-platform) commission settlement — NOT
automated Midtrans split payments — and founder-as-sole-superadmin (no per-pool
admin accounts yet).

**Explicitly deferred to Phase 2 (not built until Phase 1 proves pools/coaches
will actually transact):** automated commission-split payments, rating/trust
system, per-pool admin accounts. None of these are needed to test the real
unknown (will pools/coaches/parents accept the arrangement at all) — building
them now would be scope creep ahead of validation, per the reviewer finding below.

**Abort/descope checkpoint:** if, after approaching the existing network
(v1 client + 3 interviewed pools) about the commission arrangement, zero pools
agree to let an outside coach in, halt Phase 1 build and fall back to Approach A
(concierge listing) before writing more schema code.

### Approach C: WhatsApp Concierge Manual (zero code) — NOT chosen
Run the marketplace concept purely manually for 2-4 weeks via WhatsApp — founder as
human matching engine, spreadsheet tracking, manual bank-transfer commission. Zero
code. Effort: XS. Risk: Very low. Rejected for the same reason as A.

## Recommended Approach

Recommendation was Approach A (cheapest way to de-risk Premise 1 and 5 before any
architecture investment). **Founder chose Approach B instead** — full marketplace
architecture from the start, explicitly accepting the validation-gap risk named in
Premises 1 and 5. This is the plan of record for `/plan-eng-review`, phased per
Approach B's Phase 1/Phase 2 split above specifically to reduce that risk: Phase 1
tests the real unknown (will pools/coaches/parents accept the arrangement) without
first building the automated-payment and rating-system machinery that only matters
if Phase 1 succeeds. The validation-gap risk named in Premises 1 and 5 is not
resolved by this phasing — it is still live until the abort/descope checkpoint
above is cleared.

## Open Questions

**RESOLVED (2026-09-12, during `/plan-eng-review`):**
- **Platform legal posture: Connector** (like Gojek). Platform never holds
  member funds. Checkout routes to the affiliated pool's own Midtrans account;
  Payment stays `manual_pending`; commission settles off-platform in Phase 1.
  Confirms the Payment schema sketch above as the locked shape, not just a
  provisional assumption — no funds-holding fields needed in Phase 1.
- **Pricing/commission: platform-set flat commission percentage**, applied to
  whatever price the pool already charges (not a coach-set per-affiliation
  price). Provisional rate: **15%**, adjustable without a schema change (it's
  a config value, not a structural one) — founder can tune this after the
  first real conversations with the 3 interviewed pools. Schema implication:
  Pool (or a platform-wide config) needs one commission-percentage field, NOT
  a per-PoolAffiliation price field — this simplifies Phase 1 vs. the
  coach-set alternative.

**Blocks Phase 2 only (not Phase 1 — Phase 1 uses manual settlement, so this
can wait):**
- Midtrans marketplace/split-settlement API availability — not yet verified
  whether the account tier supports split disbursement to multiple parties
  (pool + coach + platform cut). Confirm before Phase 2 automated-split work
  starts, not before Phase 1 schema lock.

**Does not block schema, but must be resolved before real users onboard:**
- Liability/consent model (who owns facility risk vs teaching risk; parental
  consent form design, since most bookings are for children).
- Coach certification/verification process.
- Conflict-of-interest risk with pools who already have in-house coaches (may
  see this as poaching) — affects initial partner outreach, since the "old
  network" GTM plan above targets exactly the pools with existing in-house
  coach relationships. This could surface as friction in the very first
  conversations, not a later-stage problem.

## Failure modes

| Codepath | Realistic failure | Test? | Error handling? | User sees |
|---|---|---|---|---|
| Availability creation, unique(coachId,timeslot) | Coach's client retries a slow request, submits slot twice | Yes (new P1 test) | DB constraint rejects 2nd | Clear "slot already exists" — not silent |
| Booking creation row lock | Two members tap "book" within milliseconds | Yes (new P1 test) | `FOR UPDATE` + status check | One sees success, one sees "slot just taken" |
| Checkout, pool with no midtransMerchantId | Member tries to pay before pool finishes Midtrans KYC | **GAP — no test, no UI handling defined** | **None specified** | **Risk: silent failure or raw error** — flagged as critical gap, needs a fallback UI (cash/manual-transfer prompt) before Phase 1 ships |
| Onboarding seed script run twice | Founder re-runs script by mistake | **GAP — no idempotency check specified** | **None specified** | Risk: duplicate Pool/PoolAffiliation rows — flagged as critical gap, script needs an existence check before insert |
| Commission summary report, pool with zero bookings | Report queries a pool with no Payment rows yet | No | Should short-circuit to zero | Empty state, not a crash — low risk, straightforward |

**Critical gaps** (no test AND no error handling AND would be silent): the
no-merchant-account checkout path and the seed-script idempotency gap. Both
should get explicit handling before Phase 1 ships, not deferred.

## Worktree parallelization strategy

| Step | Modules touched | Depends on |
|---|---|---|
| Schema + migration (Pool, PoolAffiliation, Availability changes, commission field) | `prisma/` | — |
| Onboarding seed script (role downgrade, idempotency check) | `scripts/` (new) | Schema |

| Midtrans checkout: per-pool merchant routing + no-merchant-account fallback UI | `src/app/api/payment/` | Schema |

Lane A: Schema → Onboarding script (sequential, shared `prisma/`).
Lane B: Booking-lock wiring (independent once schema lands).
Lane C: Pool-first browse UI + coach shortcut page (independent once schema lands).
Lane D: Commission report + checkout merchant routing (independent once schema lands).

Execution order: land Schema first (blocks everything). Then launch B, C, D in
parallel worktrees — none share module directories. Merge all three. Onboarding
script (Lane A's second half) can run anytime after schema, independent of B/C/D.
